# Coordinator Guide

This guide covers the supported `adamant-ModpackLib.modpack` contract for
coordinator mods. New pack coordinators are normally generated by
[`ModpackBootstrap`](https://github.com/h2-modpack/ModpackBootstrap).

## What The Coordinator Owns

The coordinator owns:

- `packId`
- Chalk config
- default profiles
- GUI registration
- module order
- optional coordinator-specific Quick Setup content

Lib's modpack subsystem owns:

- module discovery
- config hashing and profile load
- HUD fingerprint
- main pack window
- pack-level enable/disable behavior

## Bootstrap Pattern

Recommended coordinator shape:

```lua
local lib = rom.mods["adamant-ModpackLib"]
assert(lib and type(lib.modpack) == "table",
    "my-coordinator: adamant-ModpackLib.modpack is not loaded")
local Modpack = lib.modpack

local config = chalk.auto("config.lua")
local loader = reload.auto_single()
local defaultProfiles = {}

local function drawPackQuickContent(ctx)
    -- Optional coordinator quick controls.
end

local function rebuildModpack()
    -- Re-run the same create path used by the coordinator's lazy bootstrap.
end

mods.on_all_mods_loaded(function()
    Modpack.registerCoordinator(PACK_ID, "My Modpack", config, rebuildModpack)
end)

local function ensureModpack()
    local ok = Modpack.createPack(PACK_ID, config, #config.Profiles, defaultProfiles, {
        moduleOrder = {
            "ExampleModule",
        },
        drawPackQuickContent = drawPackQuickContent,
    })
    return ok == true
end

local function registerGui()
    local callbacks = Modpack.createGuiCallbacks(PACK_ID)
    rom.gui.add_imgui(callbacks.render)
    rom.gui.add_always_draw_imgui(function()
        ensureModpack()
        callbacks.alwaysDraw()
    end)
    rom.gui.add_to_menu_bar(callbacks.menuBar)
end

modutil.once_loaded.game(function()
    loader.load(registerGui)
end)
```

Coordinators normally defer `createPack(...)` until the first always-draw tick
after game-load callbacks. This lets module activation finish before discovery
without relying on dependency-pin callback ordering.

## `Modpack.registerCoordinator(packId, displayName, config, rebuildCallback?)`

Registers coordinator metadata and the optional structural rebuild callback for
one pack id.

Required:

- `packId`
- `displayName`
- `config`

`config` must contain:

- `ModEnabled`

When clearing a registration, pass `nil` config and `nil` display name.

`rebuildCallback(reason)` is called when a coordinated module reports a
structural change that requires pack rediscovery. Return `true` when the pack
was rebuilt.

## `Modpack.createPack(packId, config, numProfiles, defaultProfiles, opts?)`

Creates or replaces the pack runtime for `packId`.

Required:

- `packId`
- `config`
- `numProfiles`
- `defaultProfiles`

`config` must contain:

- `ModEnabled`
- `DebugMode`
- `Profiles`

Optional `opts` fields:

- `moduleOrder`
  Ordered module ids to pin first in the sidebar. Unknown entries are warned
  and ignored.
- `drawPackQuickContent(ctx)`
  Coordinator-owned Quick Setup content. See [QUICK_SETUP.md](QUICK_SETUP.md).
- `hideHashMarker`
  Suppresses the HUD hash marker while keeping the rest of the coordinator
  surface active.

`createPack(...)` validates runtime prerequisites, logs construction failures,
and returns `false, nil, err` instead of throwing to the coordinator.

## `Modpack.createGuiCallbacks(packId)`

Returns callbacks for coordinator-owned ROM GUI registration:

- `callbacks.render`
- `callbacks.alwaysDraw`
- `callbacks.menuBar`

Register these from the coordinator plugin so ROM attributes the UI to the pack
plugin context.

## Discovery Contract

The modpack subsystem discovers modules through Lib's live-module registry:

```lua
liveModule.getPackId() == PACK_ID
```

Direct live-module lookup is keyed by `pluginGuid`. Pack discovery filters the
registry by prepared live-module identity instead of looking modules up by
module id.

Each discovered coordinated module must expose:

- `liveModule.getModuleId()`
- `liveModule.getMeta().name`
- `liveModule.getStorage()`
- `liveModule.drawTab()`

`liveModule.drawQuickContent()` is optional.

These are full Lib live-module methods. The module-authored callbacks registered
with Lib receive `(host, ui)`. Lib owns module definition preparation and
lifecycle validation before the live module is published, so modpack discovery
trusts Lib-created live modules.

Runtime state transitions are routed through live-module lifecycle methods:

- `liveModule.setEnabled(enabled)`
- `liveModule.commitIfDirty()`

Pack disable snapshots each discovered module's current `Enabled` value, then
disables modules through Lib's live-module pack-suspension lifecycle. Pack
enable restores that snapshot through the matching lifecycle path and clears it
after a successful restore. The snapshot is persisted in Lib-managed internal
storage, so a disabled pack can survive a full game restart and still restore
the prior module mix when re-enabled.

## Window Model

The modpack UI renders:

- one sidebar tab per discovered module
- Quick Setup
- Profiles
- Dev

Module tabs are simple:

- the modpack UI renders the enable checkbox
- the modpack UI snapshots live modules at the start of the UI operation
- the selected live module's `drawTab()` runs when enabled
- if staged state is dirty after draw, the snapshot live module commits through
  `commitIfDirty()`

## Quick Setup

Quick Setup renders in this order:

1. built-in profile quick selector
2. coordinator-owned content from `opts.drawPackQuickContent(ctx)`
3. each discovered enabled module with quick content support

See [QUICK_SETUP.md](QUICK_SETUP.md).

## Reload Behavior

Coordinator bootstrap normally re-enters the same `Modpack.createPack(...)`
path from its lazy pack creation function.

The coordinator owns creation arguments and re-calls `Modpack.createPack(...)`
when the coordinator layer reloads. Lib replaces pack state for the same
`packId` while preserving that pack's stable HUD/index slot.

Coordinated module behavior reloads do not rebuild the pack. Instead:

- discovery metadata remains static for the current pack instance
- UI and hash paths snapshot the module's live module at the start of each
  operation

Coordinated module structural reloads can request a pack rebuild through the
callback registered with `Modpack.registerCoordinator(...)`. If no callback is
registered or the request is rejected, the module warns that a full reload is
required.

## Hash And Profiles

Hash/profile behavior is built on:

- module enable state
- validated persisted storage roots

Profile load:

- stages decoded persisted values through each live module/state plumbing
- flushes staged managed values to config
- reapplies enabled/runtime state
- rolls the operation back on failure

Compatibility-sensitive details are documented in [HASH_PROFILE_ABI.md](HASH_PROFILE_ABI.md).

## Runtime Transactions

Modpack-owned operations are transactional when practical:

- per-entry enable/disable
- coordinator master `ModEnabled` toggle
- managed staged-state commit
- profile/hash load

The intended outcome is:

- commit the new state
- or restore the previous persisted/runtime state and warn
