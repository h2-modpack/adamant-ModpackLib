## Current Shape

- `module.hooks.*` declarations are captured before activation through
  `module_bootstrap/module/declaration_surface.lua`.
- Hook declarations are plain data in `core/hooks/declarations.lua`.
- Activation installs receipts through `core/hooks/adapters/module_install.lua`
  and `core/hooks/owner_install.lua`.
- Stable hot-reload dispatchers live in `core/hooks/dispatchers.lua`.
- Raw ModUtil registration details are isolated in
  `core/hooks/modutil_registry.lua`.
- System hooks use the same declaration/receipt path through
  `core/hooks/adapters/system_declarations.lua`.

## Findings

- `keep`: The main layering is sound. Author declarations do not call ModUtil
  directly; activation owns the receipt, and dispatchers keep the hot-reload
  stable ModUtil anchors.
- `keep`: Context wraps have the right current shape. The outer callback gets
  `(host, runtime, context, ...)`; inner `context.wrap(...)` handlers get the
  raw ModUtil wrap signature and close over the outer callback state.
- `keep`: Tests cover the important lifecycle edges: omitted hook refresh,
  owner pruning, override restore, context-surface closure, failed declaration
  refresh, failed activation rollback, and partial commit rollback.
- `delete`: `core/hooks/modutil_registry.lua` still had support for
  non-function `Path.Override(...)` replacements. Public hook declarations now
  reject non-function replacements, and dispatcher refresh installs function
  dispatcher replacements only, so the lower-level non-function override branch
  was removed.
- `document`: `API.md` and `HOOKS.md` are mostly aligned with implementation.
  A future doc polish pass can tighten wording around "module owner id" and
  explicitly mention that function overrides are the only supported public
  override form.

## Result

Hooks are coherent after removing the stale non-function override path.
